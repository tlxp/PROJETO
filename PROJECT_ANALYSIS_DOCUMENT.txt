--------------------------------------------------------------------------------
1. PROJECT OVERVIEW
--------------------------------------------------------------------------------

1.1 Nome e propósito
--------------------
O projeto designa-se RAT Analyzer (Remote Access Trojan Analyzer) e consiste numa
aplicação de análise de malware que combina:

  • Análise estática (engenharia reversa, descompilação, deteção de padrões)
  • Análise comportamental/dinâmica (execução em sandbox VM com monitorização)

Objetivo de negócio: permitir a analistas de segurança e investigadores avaliar
ficheiros executáveis (.exe, .dll) quanto a comportamento malicioso, obfuscação
e risco, com suporte a relatórios estruturados e, no futuro, a um assistente de
IA para interpretação do código reverso.

1.2 Stack tecnológico atual
---------------------------
  • Backend: Python (FastAPI), orquestração de análise (RATAnalyzer), job store
    SQLite, fila opcional Redis/RQ, drivers de VM (stub, Hyper-V, Proxmox).
  • Frontend web: React (Vite) + TypeScript, shadcn/ui, visualização de código
    (pseudo-C, IL, relatório), drop de ficheiros, polling de jobs.
  • Cliente desktop: WPF (C# / XAML, .NET 8) para seleção de ficheiro, análise
    estática e publicação de resultados no backend, abertura de resultados no
    browser.
  • VM Agent: aplicação ASP.NET Core mínima que corre dentro da VM de sandbox;
    recebe amostra por HTTP, executa-a e devolve relatório de comportamento.
  • Ferramentas de análise: ILSpy (descompilação .NET), Ghidra/PyGhidra
    (pseudo-C para binários nativos), YARA, módulos internos (strings, deobfuscação,
    risk scoring, report generation).

1.3 Escopo do documento
----------------------
Este documento descreve o domínio do problema, utilizadores, cenários de uso,
user stories, dependências entre funcionalidades, fluxos críticos, recomendações
de arquitetura e definição de MVP, com vista a evoluir o sistema para uma
plataforma completa de análise de malware em C#/XAML (conforme objetivo final
indicado) e a alinhar a implementação atual (Python/React/WPF) com esse objetivo.

2. PROBLEM DOMAIN ANALYSIS
--------------------------------------------------------------------------------

2.1 Domínio principal
--------------------
O domínio é Segurança Informática / Análise de Malware, com subdomínios:

  (a) Análise estática
      — Inspeção do ficheiro sem execução: metadados, strings, imports, padrões
        (YARA), descompilação (C#/IL para .NET; pseudo-C para nativos), deteção
        de obfuscação e tentativas de deobfuscação, scoring de risco.

  (b) Análise comportamental (dinâmica)
      — Execução controlada em ambiente isolado (VM/sandbox), monitorização de
        alterações no sistema (ficheiros, registry, processos, APIs), geração de
        relatório de comportamento e restauro do ambiente a um snapshot limpo.

  (c) Inteligência de ameaças (planeado)
      — Consulta a APIs públicas (ex.: MalwareBazaar) para verificar se o hash
        do ficheiro é conhecido (família, classificação, data de deteção).

  (d) Apoio à interpretação (planeado)
      — Assistente de IA que, dado um trecho de pseudo-código ou função, devolve
        resumo, explicação do comportamento e possíveis riscos.

2.2 Entidades e conceitos
-------------------------
  • Amostra (Sample): ficheiro .exe/.dll submetido para análise.
  • Job de análise: unidade de trabalho com tipo (static / dynamic / both),
    estado (queued, running, completed, failed), resultados estáticos e/ou
    dinâmicos, e metadados (nome do ficheiro, SHA256, timestamps).
  • Relatório estático: texto e/ou estruturas (funções, indicadores assinalados,
    risco, YARA, deobfuscação).
  • Relatório dinâmico: eventos de sistema (ficheiros, registry, processos,
    rede, APIs) capturados na VM.
  • VM / Sandbox: ambiente isolado (Hyper-V, Proxmox ou stub) onde a amostra
    é executada; VM Agent dentro da VM recebe o ficheiro, executa-o e reporta.
  • Indicadores assinalados (flagged): funções ou strings que o sistema marca
    como suspeitas; utilizados para highlight no pseudo-código e no relatório.

2.3 Regras de negócio relevantes
--------------------------------
  • O ficheiro deve ser validado (existência, tipo suportado) antes de iniciar
    a análise.
  • Análise estática pode ser executada de forma síncrona (upload → resultado)
    ou assíncrona (job → polling).
  • Análise dinâmica é sempre assíncrona e depende de um driver de VM
    configurado (stub devolve dados simulados; Hyper-V/Proxmox requerem VM e
    VM Agent).
  • Resultados de análise estática podem ser publicados pelo cliente (ex.: WPF)
    via endpoint dedicado (upload_static), criando um job apenas para
    histórico e visualização no frontend.
  • O histórico de análises é persistido em SQLite (job_id, tipo, estado,
    static_json, dynamic_json) e opcionalmente em disco (last_analysis.json,
    relatórios .txt).

2.4 Riscos e restrições do domínio
----------------------------------
  • Execução de malware: apenas em VM isolada; nunca no host de análise.
  • Configuração da VM (nome, snapshot, agent URL) deve vir de ambiente/conf,
    não de input do utilizador, para evitar injeção de comandos.
  • Dados sensíveis: amostras e relatórios podem conter informação confidencial;
    acesso e retenção devem ser considerados do ponto de vista de segurança e
    privacidade.
  • Ferramentas externas (ILSpy, Ghidra): dependem de caminhos e versões
    configurados; falhas de descompilação não devem derrubar todo o pipeline.

4. PERSONAS
--------------------------------------------------------------------------------

4.1 Analista de Segurança (Principal)
-------------------------------------
  Nome: Ana (persona principal).
  Perfil: Trabalha em SOC ou equipa de resposta a incidentes. Precisa de
  avaliar rapidamente ficheiros suspeitos (ex.: anexos de phishing, binários
  de endpoints) e decidir se são maliciosos e qual o nível de risco.
  Objetivos: Obter relatório estático (funções suspeitas, padrões YARA, risco)
  e, quando necessário, relatório comportamental (ficheiros/registry/processos).
  Dores: Ferramentas dispersas; falta de visão única (estático + dinâmico);
  dificuldade em interpretar pseudo-código sem contexto.
  Uso do sistema: Seleciona ficheiro na aplicação (WPF ou Web), corre análise
  estática e/ou dinâmica, consulta relatório e código destacado; no futuro,
  usa o assistente de IA para explicar funções específicas.

4.2 Investigador de Malware
----------------------------
  Nome: Rui.
  Perfil: Foca-se em engenharia reversa e categorização de famílias de malware.
  Objetivos: Descompilação de qualidade (C#/IL e pseudo-C), deteção de
  obfuscação e deobfuscação, e cruzamento com bases de inteligência (ex.:
  MalwareBazaar) para saber se o hash já é conhecido.
  Dores: Integrar várias ferramentas manualmente; falta de um único fluxo
  que una estático, dinâmico e threat intel.
  Uso do sistema: Usa análise estática aprofundada (incl. Ghidra), consulta
  relatórios de obfuscação e, quando a funcionalidade existir, verificação de
  hash em API externa e assistente de IA para funções complexas.

4.3 Operador de Laboratório (Sandbox)
--------------------------------------
  Nome: Carlos.
  Perfil: Responsável pela infraestrutura de sandbox (VMs Hyper-V ou Proxmox).
  Objetivos: Garantir que a análise dinâmica corre em VM isolada, que o VM
  Agent está acessível e que o ambiente é restaurado após cada execução.
  Dores: Configuração manual de VMs e de variáveis de ambiente (VM name,
  snapshot, agent URL); necessidade de canal fiável VM → host para relatórios.
  Uso do sistema: Configura SANDBOX_VM_DRIVER, HYPERV_VM_NAME, VM_AGENT_BASE_URL,
  etc.; monitoriza logs do backend e do VM Agent; no futuro, pode depender de
  canal serial virtual para recolha de relatório se HTTP não for desejado.

4.4 Desenvolvedor / Integrador
-------------------------------
  Nome: Marta.
  Perfil: Desenvolve ou mantém a aplicação; integra novas regras YARA, novos
  endpoints ou a migração para uma aplicação desktop em C#/XAML.
  Objetivos: API estável, documentação clara, testes e arquitetura que permitam
  evoluir para uma plataforma completa.
  Uso do sistema: Consome a API (POST /api/analyze, /api/analysis, GET
  /api/analysis/{id}), consulta histórico em DB e relatórios em disco;
  estende módulos de análise e drivers de VM.

5. USAGE SCENARIOS
--------------------------------------------------------------------------------

5.1 Cenário 1: Análise estática rápida (cliente WPF)
----------------------------------------------------
  Ator: Ana (Analista de Segurança).
  Pré-condição: Backend e frontend web estão a correr; WPF configurado com
  ApiBaseUrl e FrontendUrl corretos.
  Fluxo principal:
    1. Ana abre a aplicação WPF e arrasta um ficheiro .exe para a área de drop.
    2. Clica em "Análise estática".
    3. A aplicação envia o ficheiro para POST /api/analyze e aguarda resposta.
    4. Com o resultado, envia POST /api/analysis/upload_static para registar
       um job e obter jobId.
    5. Abre no browser a URL FrontendUrl/resultados?jobId=...
    6. No frontend, Ana vê o relatório, pseudo-código (C) e IL com funções e
       indicadores assinalados e nível de risco.
  Pós-condição: Job fica no histórico (SQLite); Ana pode partilhar o link ou
  rever o resultado mais tarde.

5.2 Cenário 2: Análise estática com streaming (frontend web)
------------------------------------------------------------
  Ator: Ana.
  Pré-condição: Backend e frontend React a correr.
  Fluxo principal:
    1. Ana acede à página principal do frontend e faz drop de um .dll.
    2. Escolhe modo "Estática" e inicia a análise.
    3. O frontend chama POST /api/analyze_stream (multipart); a resposta é
       NDJSON com eventos de progresso e, no fim, o objeto de resultado.
    4. Durante a análise, Ana vê mensagens em tempo real (ex.: "Descompilação
       .NET...", "Scan YARA...").
    5. No fim, são apresentados o relatório, o código C e o IL com highlights.
  Pós-condição: Resultado visível na mesma sessão; opcionalmente pode ser
  guardado como job (conforme implementação de /api/analyze_stream).

5.3 Cenário 3: Análise combinada (estática + dinâmica) por job
--------------------------------------------------------------
  Ator: Rui (Investigador).
  Pré-condição: Backend com driver de VM configurado (ex.: Hyper-V); VM Agent
  ativo dentro da VM.
  Fluxo principal:
    1. Rui envia o ficheiro via POST /api/analysis com analysis_type=both
       (ou via UI que submete multipart e tipo "both").
    2. O backend cria job, grava a amostra em sandbox_jobs/{job_id}/ e
       enfileira (ou executa em thread) _run_job.
    3. Primeiro corre análise estática; depois run_dynamic_analysis(job):
       restaura snapshot, inicia VM, upload para o agent, run, GET report.
    4. Rui faz polling a GET /api/analysis/{job_id} até status=completed.
    5. A resposta inclui staticResult e dynamicResult; o frontend mostra ambos
       (relatório estático + eventos/comportamento dinâmico).
  Pós-condição: Job completo em DB e em memória; VM restaurada (conforme
  implementação do driver).

5.4 Cenário 4: Consulta de resultado histórico por jobId
---------------------------------------------------------
  Ator: Ana ou Rui.
  Pré-condição: Existe um job_id previamente criado (por WPF ou pelo frontend).
  Fluxo principal:
    1. O utilizador acede a /resultados?jobId=xxx (ou insere o jobId na UI).
    2. O frontend chama GET /api/analysis/xxx.
    3. O backend resolve o payload: primeiro memória (AnalysisJob), depois
       job_store (SQLite), depois fallback para last_analysis.json em
       sandbox_jobs/xxx/out/.
    4. O frontend renderiza staticResult (report, cCode, ilCode, flags) e, se
       existir, dynamicResult.
  Pós-condição: Visualização consistente com a do momento em que o job foi
  concluído.

5.5 Cenário 5: Análise dinâmica com driver stub (desenvolvimento)
-----------------------------------------------------------------
  Ator: Marta (Desenvolvedora).
  Objetivo: Testar o fluxo de jobs sem uma VM real.
  Fluxo: Submete job com analysis_type=dynamic. O driver stub devolve
  DynamicAnalysisOutput simulado (timeline, processes, network vazios ou
  de teste). Marta verifica que o job completa e que dynamicResult aparece
  na API e no frontend.

5.6 Cenário 6 (Planeado): Verificação de hash em MalwareBazaar
--------------------------------------------------------------
  Ator: Rui.
  Fluxo: Após upload (ou após análise estática), o sistema calcula SHA256 da
  amostra e chama uma API pública (ex.: MalwareBazaar); mostra família,
  classificação e data de deteção na UI.

5.7 Cenário 7 (Planeado): Assistente de IA para uma função
----------------------------------------------------------
  Ator: Ana ou Rui.
  Fluxo: Na vista de pseudo-código, o utilizador clica num botão associado a
  uma função. O frontend envia o código da função a uma API de IA; a resposta
  (resumo, comportamento, riscos) é exibida na interface.

6. USER STORIES
--------------------------------------------------------------------------------

6.1 Análise estática
--------------------
  US-1.1  Como analista, quero selecionar um ficheiro .exe ou .dll na aplicação
          para que possa submetê-lo à análise estática.
  US-1.2  Como analista, quero que o sistema descompile ficheiros .NET (C#/IL)
          automaticamente para que eu possa inspecionar o código fonte
          recuperado.
  US-1.3  Como analista, quero ver pseudo-código C para binários não-.NET para
          que eu possa analisar a lógica sem depender apenas de assembly.
  US-1.4  Como analista, quero um relatório que inclua funções e indicadores
          assinalados como suspeitos para que eu saiba onde focar a revisão.
  US-1.5  Como analista, quero ver um nível de risco (score e nível) no
          relatório para que eu possa priorizar amostras.
  US-1.6  Como analista, quero ver resultados de scan YARA (regras RAT/C2/evasão)
          no relatório para que eu possa correlacionar com regras conhecidas.
  US-1.7  Como utilizador do frontend, quero ver o progresso da análise em
          tempo real (streaming) para que eu saiba que o sistema está a
          processar.

6.2 Obfuscação e deobfuscação
-----------------------------
  US-2.1  Como investigador, quero que o sistema detete tentativas de
          obfuscação (strings XOR, Base64, etc.) para que eu saiba que o
          binário pode estar a esconder comportamento.
  US-2.2  Como investigador, quero que as ocorrências de obfuscação sejam
          assinaladas e, quando possível, que o sistema tente deobfuscar e
          mostre o resultado no relatório.

6.3 Inteligência de ameaças (planeado)
--------------------------------------
  US-3.1  Como investigador, quero que o sistema consulte uma API de
          inteligência (ex.: MalwareBazaar) com o hash do ficheiro para que
          eu saiba se a amostra já é conhecida e qual a família/classificação.
  US-3.2  Como analista, quero ver a data de deteção e referências conhecidas
          quando o hash for encontrado na API.

6.4 Análise comportamental (sandbox)
------------------------------------
  US-4.1  Como analista, quero submeter um ficheiro para análise dinâmica em
          sandbox para que o sistema execute a amostra de forma isolada e
          registe o comportamento.
  US-4.2  Como analista, quero ver no relatório dinâmico alterações em
          ficheiros, registry, processos e chamadas a APIs sensíveis para que
          eu possa avaliar o impacto.
  US-4.3  Como operador, quero que a VM seja restaurada a um snapshot limpo
          após cada análise para que o próximo run não seja contaminado.
  US-4.4  Como utilizador, quero poder escolher apenas estática, apenas
          dinâmica ou ambas no mesmo job para que eu adapte o fluxo ao meu
          contexto.

6.5 Comunicação VM → Host (planeado)
------------------------------------
  US-5.1  Como operador, quero que o relatório gerado dentro da VM seja
          transferido para o host por um canal fiável (ex.: porta serial
          virtual) quando HTTP não for adequado.

6.6 Assistente de IA (planeado)
-------------------------------
  US-6.1  Como analista, quero clicar numa função no pseudo-código e obter um
          resumo e explicação em linguagem natural para que eu compreenda mais
          rapidamente o comportamento.
  US-6.2  Como analista, quero que a IA indique possíveis riscos (ex.:
          persistência, C2, keylogging) associados à função.

6.7 Interface e histórico
-------------------------
  US-7.1  Como utilizador WPF, quero que após a análise estática seja aberto
          o browser na página de resultados com o jobId correto para que eu
          veja o relatório e o código sem sair do fluxo.
  US-7.2  Como utilizador, quero aceder a um resultado passado através do
          jobId (ex.: /resultados?jobId=xxx) para que eu possa partilhar ou
          rever análises anteriores.
  US-7.3  Como utilizador, quero ver uma lista (histórico) de análises com
          filtros básicos para que eu possa encontrar jobs antigos.

8. CRITICAL USER FLOWS
--------------------------------------------------------------------------------

8.1 Fluxo crítico 1: Análise estática completa (fim-a-fim)
----------------------------------------------------------
  Passos:
    1. Utilizador seleciona ficheiro (.exe ou .dll) na UI (WPF ou React).
    2. Cliente envia ficheiro (multipart) para POST /api/analyze ou
       POST /api/analysis?analysis_type=static.
    3. Backend valida e, no caso de job, cria diretório sandbox_jobs/{job_id},
       grava amostra, insere registo em job_store (status=queued), enfileira ou
       inicia _run_job em thread.
    4. _run_job marca status=running; chama _run_static(job).
    5. _run_static instancia RATAnalyzer com sample_path e output_dir=job
       output_dir; executa analyze(): file_info, descompilação .NET (se
       aplicável), StaticAnalyzer, Deobfuscator, YaraScanner, Ghidra (se
       disponível), RiskScorer, ReportGenerator; extrai flagged_indicators e
       flagged_functions; grava last_analysis.json e relatório .txt no output_dir.
    6. _run_static constrói AnalysisResult (report, cCode, ilCode, riskScore,
       riskLevel, flaggedIndicators, flaggedFunctions) e opcionalmente aplica
       summarize_c_code para limitar tamanho do cCode; devolve ao job.
    7. job_store.update_results e update_status(completed).
    8. Cliente (se job) faz GET /api/analysis/{job_id} e recebe staticResult;
       (se /api/analyze) recebe diretamente o JSON na resposta.
    9. Frontend renderiza relatório, painéis de código (C, IL) com highlights
       para flaggedIndicators e flaggedFunctions.
  Pontos de falha: Ficheiro inexistente ou tipo não suportado; falha de
  ILSpy/Ghidra (tratada com fallback e mensagem no relatório); timeout;
  tamanho excessivo de cCode (mitigado por summarize_c_code).

8.2 Fluxo crítico 2: Publicação de resultado estático pelo WPF
--------------------------------------------------------------
  Passos:
    1. WPF já obteve resultado de POST /api/analyze (report, cCode, ilCode,
       riskScore, riskLevel, flaggedIndicators, flaggedFunctions).
    2. WPF envia POST /api/analysis/upload_static com body StaticAnalysisUpload
       (fileName, report, cCode, ilCode, riskScore, riskLevel, flaggedIndicators,
       flaggedFunctions).
    3. Backend gera job_id, chama job_store.insert_job (analysis_type=static,
       status=completed), job_store.update_results com static_json construído
       a partir do body; opcionalmente grava em sandbox_jobs/{job_id}/out/ para
       consistência.
    4. Backend devolve { jobId }.
    5. WPF abre browser em FrontendUrl/resultados?jobId=...
    6. Frontend chama GET /api/analysis/{jobId}; backend devolve payload com
       staticResult; UI mostra relatório e código.
  Pontos de falha: Backend indisponível; CORS; frontend não a correr na URL
  configurada.

8.3 Fluxo crítico 3: Análise dinâmica com Hyper-V
-------------------------------------------------
  Passos:
    1. Job criado com analysis_type=dynamic ou both; amostra em
       sandbox_jobs/{job_id}/.
    2. _run_job chama run_dynamic_analysis(job); vm_orchestrator obtém driver
       via SANDBOX_VM_DRIVER=hyperv e HyperVConfig a partir de env.
    3. HyperVVMDriver.run(job): valida config; executa Restore-VMSnapshot e
       Start-VM via PowerShell; espera VM Agent (HTTP) ficar pronto.
    4. _agent_upload(job): envia ficheiro para VM_AGENT_BASE_URL/api/upload.
    5. _agent_run(timeout): POST .../api/run.
    6. _agent_get_report(): GET .../api/report; parse JSON (stdout, stderr,
       exitCode, estruturas de comportamento).
    7. Driver devolve DynamicAnalysisOutput; job.dynamic_result é preenchido;
       job_store.update_results com dynamic_json.
    8. Cliente faz GET /api/analysis/{job_id}; frontend mostra dynamicResult
       (summary, behavior).
  Pontos de falha: VM ou snapshot inexistentes; VM Agent não responde; timeout
  de execução; rede entre host e VM inacessível. Política: falhar com erro
  explícito, não inventar resultados.

8.4 Fluxo crítico 4: Recuperação de resultado por jobId (fallback)
------------------------------------------------------------------
  Passos:
    1. Cliente chama GET /api/analysis/{job_id}.
    2. Backend tenta get_job(job_id) em memória; se existir, devolve to_dict().
    3. Se não, job_store.get_job_row(job_id); se existir, monta payload com
       staticResult/dynamicResult a partir das colunas static_json/dynamic_json.
    4. Se não houver linha na DB, procura sandbox_jobs/{job_id}/out/
       last_analysis.json; lê report_path, consolidated_file, flagged_indicators,
       flagged_functions, etc.; constrói static_result (report, cCode, ilCode)
       com summarize_c_code e devolve payload mínimo.
    5. Se nada for encontrado, devolve 404.
  Garante que jobs antigos (criados antes da persistência em DB ou com DB
  corrompida) ainda possam ser visualizados desde que o diretório do job e
  last_analysis.json existam.

9. ARCHITECTURE RECOMMENDATIONS
--------------------------------------------------------------------------------

9.1 Alinhamento com o objetivo final (C# / XAML)
------------------------------------------------
  O objetivo declarado é uma aplicação em C# e XAML. Recomendações:
  • Manter a API REST como contrato estável: qualquer cliente (WPF, React,
    futura app C# única) deve consumir os mesmos endpoints. Isso permite
    migrar a orquestração e a lógica de análise para C# em fases, mantendo
    compatibilidade.
  • Considerar uma camada de serviços no backend (Python ou futuro C#) que
    separe: (1) API HTTP, (2) orquestração de jobs, (3) execução de
    ferramentas (ILSpy, Ghidra, YARA). Assim, a migração pode começar pela
    orquestração e pela integração com ILSpy/Ghidra em processo ou subprocesso
    a partir de C#.
  • WPF como cliente principal a curto prazo: consolidar todos os fluxos
    (estático, dinâmico, histórico) na aplicação WPF, reduzindo a dependência
    do browser para resultados; o frontend React pode permanecer como
    alternativa ou para uso em laboratório partilhado.

9.2 Backend e jobs
------------------
  • Manter job_store (SQLite) como fonte de verdade para histórico;
    last_analysis.json como cache por job e fallback para leitura.
  • Definir política de retenção: limpeza periódica de sandbox_jobs antigos
    e, se necessário, de registos na DB, com possibilidade de exportar
    relatórios antes de apagar.
  • Em ambientes com múltiplos workers, considerar fila (Redis/RQ ou
    equivalente em C#) para evitar corrida no mesmo job; garantir que apenas
    um worker processa um dado job_id.

9.3 VM e sandbox
----------------
  • Manter abstração VM Driver (stub, hyperv, proxmox): facilita testes e
    deploy em diferentes infraestruturas.
  • Documentar variáveis de ambiente obrigatórias por driver (HYPERV_VM_NAME,
    VM_AGENT_BASE_URL, etc.) e validar no arranque do backend.
  • Se for introduzido canal Serial Port Virtual VM → host: definir formato
    do relatório (ex.: texto delimitado ou JSON por linha) e tratamento de
    falhas de leitura/timeout no host.

9.4 Segurança
-------------
  • Não aceitar nomes de VM ou paths de snapshot vindos do utilizador; usar
    apenas config/env.
  • Limitar tamanho de upload e tempo de execução (timeouts) para evitar DoS.
  • Considerar autenticação e autorização na API se o sistema for exposto
    além de localhost (ex.: API key ou JWT para clientes WPF/React).

9.5 Funcionalidades planeadas
-----------------------------
  • MalwareBazaar (ou similar): novo módulo no backend que, dado um hash,
    chama a API e devolve família/classificação; expor no resultado do job
    (ex.: novo campo threat_intel no staticResult).
  • Assistente de IA: endpoint opcional (ex.: POST /api/explain_function) que
    recebe código de uma função e devolve resumo/riscos; o frontend chama-o
    ao clicar no botão da função. Considerar rate limit e custo de API externa.
  • Relatório dinâmico rico: VM Agent pode evoluir para capturar Sysmon/ETW
    ou hooks de API e enviar eventos estruturados; o backend agrega e o
    frontend mostra timeline de eventos (ficheiros, registry, processos, rede).

10. MVP DEFINITION
--------------------------------------------------------------------------------

10.1 Objetivo do MVP
--------------------
  Entregar um fluxo mínimo utilizável que permita a um analista selecionar um
  ficheiro .exe/.dll, obter análise estática completa (relatório, pseudo-código,
  indicadores assinalados, risco) e visualizar o resultado numa interface
  única (WPF ou Web), com possibilidade de rever resultados anteriores por
  jobId.

10.2 Inclusões no MVP (já implementadas ou a fechar)
---------------------------------------------------
  • Seleção e upload de ficheiro (.exe, .dll).
  • Análise estática completa no backend (RATAnalyzer: file_info, .NET
    descompilação com ILSpy, StaticAnalyzer, Deobfuscator, YaraScanner,
    Ghidra opcional, RiskScorer, ReportGenerator).
  • Saída: relatório .txt, pseudo-código (C# consolidado ou pseudo-C), IL/asm,
    riskScore, riskLevel, flaggedIndicators, flaggedFunctions.
  • Dois modos de uso estático:
    (a) Síncrono: POST /api/analyze → resposta direta com resultado.
    (b) Assíncrono: POST /api/analysis (static) → job_id → GET
        /api/analysis/{job_id} até completed.
  • Publicação de resultado estático pelo WPF: POST /api/analysis/upload_static
    → jobId → abertura de /resultados?jobId= no browser.
  • Frontend web: drop de ficheiro, análise (stream ou job), visualização em
    três colunas (C, IL, Relatório) com highlights e histórico por jobId.
  • Persistência: job_store (SQLite), last_analysis.json e relatório em disco;
    fallback de GET /api/analysis/{job_id} para last_analysis.json quando não
    houver registo em memória/DB.
  • Análise dinâmica: pipeline de job (dynamic/both) com driver stub
    funcional; drivers Hyper-V e Proxmox implementados e configuráveis por
    env; VM Agent com upload/run/report.

10.3 Exclusões do MVP (pós-MVP)
-------------------------------
  • Integração com MalwareBazaar (ou outra API de threat intel).
  • Assistente de IA para explicação de funções.
  • Transferência de relatório VM → host por Serial Port Virtual.
  • Autenticação/autorização na API.
  • Aplicação desktop única em C# que incorpore toda a orquestração (migração
    completa do backend Python).

10.4 Critérios de conclusão do MVP
----------------------------------
  • Um analista consegue, apenas com a aplicação (WPF ou Web), submeter um
    .exe/.dll e obter um relatório estático com código destacado e nível de
    risco, e rever um resultado anterior através do jobId.
  • Um job de análise dinâmica com driver stub completa com sucesso e devolve
    dynamicResult na API e na UI; com Hyper-V configurado, o fluxo completo
    (snapshot, start, upload, run, report) executa sem erros de configuração
    quando o ambiente está correto.
  • Documentação mínima: README com passos para correr backend, frontend,
    WPF e (opcional) VM Agent; lista de variáveis de ambiente para sandbox.
