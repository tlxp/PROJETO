\chapter{Introdução}

\section{Contexto}

Este relatório apresenta o projecto final de licenciatura em Engenharia Informática da \ubi,
consagrado ao desenvolvimento do \rat: uma plataforma integrada de análise estática e dinâmica
para deteção de \emph{Remote Access Trojans} (RATs) em executáveis Windows (`.exe`, `.dll`) e
ficheiros de código fonte C\# (`.cs`).

Os RATs constituem uma das classes de malware mais preocupantes na actualidade: permitem a um
atacante controlar remotamente um sistema comprometido, recolher credenciais, exfiltrar dados e
executar comandos arbitrários. A sua deteção exige frequentemente a combinação de técnicas
\emph{offline} (análise estática do binário) e \emph{online} (observação do comportamento em
ambiente controlado), complementadas por regras de assinatura e heurísticas de scoring.

O \rat\ foi concebido no âmbito académico como ferramenta \textbf{educativa e de triagem}:
além de sinalizar indicadores de risco, expõe código descompilado, relatórios estruturados e
explicações sobre funções suspeitas, permitindo que estudantes e analistas junior compreendam
\emph{porquê} um ficheiro é considerado malicioso. Complementarmente, a interface web integra
um assistente baseado no \textbf{Google Gemini}, que permite questionar, em linguagem natural,
o significado do excerto de pseudo-C visível no painel de resultados.

\section{Motivação}

A proliferação de malware com capacidades de acesso remoto exige ferramentas acessíveis que
integrem múltiplas camadas de análise num único fluxo de trabalho. Soluções comerciais como
sandboxes na nuvem (VirusTotal, Any.Run, Hybrid Analysis) são poderosas, mas muitas vezes
inadequadas para contextos de ensino ou laboratório local, quer por custo, quer por
confidencialidade das amostras.

A motivação deste projecto assenta em quatro pilares:

\begin{itemize}
    \item \textbf{Integração} — Unificar análise estática, regras YARA, descompilação e sandbox
          num ecossistema coerente (API, interface web, aplicação desktop).
    \item \textbf{Isolamento} — Executar amostras potencialmente maliciosas numa VM Hyper-V
          sem ligação à Internet, com restauro automático a snapshot limpo.
    \item \textbf{Transparência} — Produzir relatórios detalhados (imports, strings C2, evasão,
          score de risco, pseudo-C/IL) em vez de uma simples classificação binária; opcionalmente,
          apoiar a interpretação do pseudo-C com um assistente LLM no frontend.
    \item \textbf{Reprodutibilidade académica} — Código aberto, documentação extensa, testes
          automatizados (pytest, Vitest, CI GitHub Actions) e auditoria de segurança concluída.
\end{itemize}

\section{Objectivos}

Os objectivos principais do projecto são:

\begin{enumerate}
    \item Desenvolver um \textbf{backend} em Python (FastAPI) capaz de receber amostras,
          executar um pipeline de análise estática completo e orquestrar jobs de análise
          dinâmica (\texttt{static}, \texttt{dynamic} ou \texttt{both}).
    \item Implementar uma \textbf{interface web} (React + Vite + TypeScript) com zona de
          \emph{drag-and-drop}, streaming de progresso, visualização de relatórios, pseudo-C
          (Ghidra) e IL (.NET), assistente Gemini para explicar excertos de código C, e suporte
          bilíngue (português/inglês).
    \item Disponibilizar uma \textbf{aplicação desktop WPF} (.NET~8) como ponto de entrada
          alternativo, incluindo bootstrap de dependências, escolha de idioma persistente e
          integração com a sandbox Hyper-V.
    \item Construir um \textbf{agente VM} (Minimal API .NET) e scripts PowerShell para execução
          isolada de amostras e recolha de telemetria comportamental.
    \item Definir um \textbf{modelo de scoring} (0--100) que agregue múltiplos indicadores
          (YARA, C2, evasão, packers, ofuscação, persistência).
    \item Validar o sistema com testes automatizados, amostras benignas (\texttt{benign-vm-test})
          e documentação operacional para deploy local.
\end{enumerate}

\section{Organização do Documento}

Para demonstrar as etapas do processo realizado, este relatório está organizado da seguinte forma:

\begin{enumerate}
    \item O primeiro capítulo --- \emph{Introdução} --- apresenta o projecto, a motivação, o contexto,

\chapter{Estado da Arte}

\section{Introdução}

Este capítulo contextualiza o domínio da análise de malware, com foco na deteção de RATs, e
analisa soluções existentes — estáticas, dinâmicas e híbridas — comparando-as com a abordagem
adoptada no \rat.

\section{Análise de Malware: Visão Geral}

A análise de malware divide-se tradicionalmente em duas vertentes complementares
\cite{skoudis2004,cipriano2019}:

\begin{itemize}
    \item \textbf{Análise estática} — Examina o ficheiro sem o executar: estrutura PE, secções,
          imports/exports, strings, entropia, assinaturas YARA, descompilação e deteção de
          técnicas de evasão (anti-debug, anti-VM).
    \item \textbf{Análise dinâmica} — Executa a amostra num sandbox isolado e monitoriza
          comportamento: criação de processos, alterações ao registo, ficheiros, rede e
          persistência.
\end{itemize}

\section{Tendências na Deteção de RATs e Malware}

\subsection{Sandboxes comerciais e na nuvem}

Plataformas como \emph{Any.Run} \cite{anyrun2024}, \emph{Hybrid Analysis} \cite{hybrid2019} e
\emph{Joe Sandbox} \cite{joe2020} oferecem análise dinâmica completa com relatórios interactivos.
VirusTotal \cite{virustotal2023} agrega múltiplos motores antivirus e metadados estáticos.

\subsection{Frameworks open-source}

\begin{itemize}
    \item \textbf{Cuckoo Sandbox} \cite{cuckoo2012} — Sandbox auto-alojável extensível via Python.
    \item \textbf{CAPE Sandbox} \cite{cape2021} — Orientada a configuração de famílias e C2.
    \item \textbf{YARA} \cite{yara2023} — Linguagem de regras para deteção por padrões.
    \item \textbf{Ghidra / ILSpy} \cite{ghidra2019,ilspy2024} — Descompiladores nativos e .NET.
\end{itemize}

\subsection{Deteção baseada em machine learning}

Trabalhos recentes aplicam \emph{deep learning} a features estáticas para classificação de
malware \cite{raff2018,ucar2020}. O \rat\ privilegia explicabilidade via indicadores explícitos
e código descompilado.

\chapter{Tecnologias e Ferramentas Utilizadas}
\label{ch:tecnologias}

\section{Python e FastAPI}

\textbf{Python~3.10+} foi adoptado para o backend. \textbf{FastAPI} \cite{fastapi2024} fornece
validação automática, documentação OpenAPI e streaming NDJSON (\texttt{/api/analyze\_stream}).

\section{React, Vite e TypeScript}

A interface web utiliza \textbf{React~18}, \textbf{TypeScript}, \textbf{Vite}, \textbf{Tailwind CSS},
\textbf{shadcn/ui}, \textbf{Framer Motion} e \textbf{Vitest} (34+ testes unitários). A integração
com o \textbf{Google Gemini} (\texttt{gemini-2.0-flash}) é feita directamente no browser: a API key
do utilizador é guardada em \texttt{localStorage} e nunca transita pelo backend FastAPI.

\section{.NET~8, WPF e Minimal API}

Três projectos .NET partilham \texttt{RatAnalyzer.sln}: \textbf{RatAnalyzer.Desktop} (WPF),
\textbf{VmAgent} (Minimal API na VM) e \textbf{BenignVmTest} (amostra inofensiva).

\section{YARA, Ghidra e ILSpy}

\textbf{YARA} aplica regras em \texttt{yara\_rules/}. \textbf{ILSpy CLI} descompila .NET;
\textbf{Ghidra~12+} produz pseudo-C para binários nativos PE.

\section{Hyper-V, PowerShell, SQLite}

Sandbox em \textbf{Hyper-V} (VM \texttt{MalwareSandbox}, snapshot \texttt{CleanState}, switch
\textbf{Internal} sem Internet na guest). \textbf{PowerShell} automatiza setup (\texttt{01-Setup-MalwareSandbox.ps1}),
execução de amostras (\texttt{04-Run-Sample.ps1}) e orquestração Hyper-V no Caminho A.
\textbf{SQLite} persiste jobs em \texttt{analysis.db}; \textbf{Redis + RQ} é opcional para fila distribuída.

\section{Segurança e isolamento}

O desenho adopta \emph{fail-closed} em produção: o backend recusa arrancar sem
\texttt{RATANALYZER\_API\_TOKEN} quando \texttt{RATANALYZER\_ENV=production}; o vm-agent termina
sem \texttt{VM\_AGENT\_TOKEN}. Segredos residem em \texttt{secrets/} (gitignored), gerados por
\texttt{scripts/generate-production-secrets.ps1}. Uploads HTTP são autenticados, com sanitização
de nomes, limite de tamanho e armazenamento em \texttt{DATA\_DIR} fora do repositório. A
documentação canónica de segurança está em \texttt{docs/SEGURANCA.md}.

\section{Conclusão}

A stack multi-linguagem reflecte a natureza heterogénea da análise de malware: Python para
pipeline e API, TypeScript para UX, C\# para Windows/Hyper-V, PowerShell para infraestrutura.

\textbf{Scoring de risco.} Calcular score 0--100 agregando YARA, C2, evasão, packers, ofuscação,

\fr{07} &
\textbf{Streaming de progresso.} Endpoint \texttt{/api/analyze\_stream} em NDJSON com logs

\textbf{Orquestração VM.} Dois caminhos dinâmicos: (A) backend Python + vm-agent HTTP;

\texttt{POST /api/analysis/upload\_dynamic}, reutilizando o \texttt{jobId} da análise estática
quando aplicável. \\
\fr{09} &
\textbf{Assistente Gemini no pseudo-C.} No painel de código C descompilado, o utilizador pode
configurar uma API key do Google AI Studio (armazenamento local) e perguntar, via chat, o que faz

demonstração com resposta simulada, sem chamada à API. \\

\section{Backend — Pipeline de Análise Estática}

A classe \texttt{RATAnalyzer} (\texttt{backend/rat\_analyzer.py}) orquestra o pipeline em 7 fases:

\begin{enumerate}
    \item Extração de metadados PE (\texttt{file\_info}).

\subsection{Caminho B — Scripts PowerShell}

O \texttt{04-Run-Sample.ps1} executa fases A--G: setup, boot VM, cópia de amostra e scripts,
execução destacada na guest, espera de \texttt{guest\_analysis\_done.txt}, cópia do relatório
guest$\rightarrow$host via \textbf{PowerShell Direct} ou \texttt{Copy-VMFile}, verificação
\textbf{SHA256} após a cópia, e cleanup \texttt{try/finally}.

Fluxo dentro da VM (\texttt{vm/Run-MalwareAnalysis.ps1}):
\begin{itemize}
    \item Baseline de processos, ficheiros, registry e rede.
    \item Execução da amostra com timeout configurável.
    \item Diff pós-execução; marcador \texttt{REPORT\_END;} e ficheiro
          \texttt{guest\_analysis\_done.txt} com \texttt{reportSha256} e \texttt{reportBytes}.
\end{itemize}

O host valida integridade comparando o hash e o tamanho do ficheiro copiado com o digest
registado no guest; em caso de discrepância, o relatório no host é descartado. O destino típico
é \texttt{D:\textbackslash PROJETOVM\textbackslash Reports\textbackslash analysis\_<RunId>.txt};
o JSON do run regista \texttt{report\_sha256} e \texttt{report\_hash\_verified}.

\section{Protocolo de transferência de relatório (Caminho B)}

\subsection{Implementação actual}

Após a análise, o guest grava \texttt{C:\textbackslash analysis.txt} e
\texttt{C:\textbackslash analysis\_work\textbackslash guest\_analysis\_done.txt} (JSON com
\texttt{reportSha256}, \texttt{reportBytes}, \texttt{transport=psdirect}). O host copia o
relatório com PsDirect ou \texttt{Copy-VMFile} e só aceita o ficheiro se o SHA256 e o tamanho
coincidirem com o digest do guest.

\subsection{Abordagens anteriores (arquivo)}

Versões anteriores enviavam o relatório \textbf{linha-a-linha} via COM1:
\texttt{START\_OF\_REPORT} \textrightarrow{} linhas de conteúdo \textrightarrow{}
\texttt{END\_OF\_REPORT}, com \texttt{Copy-VMFile} como fallback. Este desenho exigia VM
Generation~1 para o par COM1/pipe e mostrou-se menos robusto que a cópia directa com hash
(ver subsecção~\ref{sec:caminho-b-historico} no capítulo de implementação).
