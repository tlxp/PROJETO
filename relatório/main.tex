\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}
\markboth{Abstract}{Abstract}

This report presents \rat{}, an integrated static and dynamic analysis platform for detecting
\emph{Remote Access Trojans} (RATs) in Windows executables (and C\# source with reduced scope),
developed as the final-year project in Computer Science Engineering at \ubi{}. The solution
combines a Python backend (FastAPI) with a seven-phase pipeline (PE metadata, ILSpy, heuristics,
deobfuscation, YARA, risk scoring, native/Ghidra when needed, and reporting), a React web
interface with an optional Gemini assistant, a WPF desktop application, and an isolated
Hyper-V sandbox with two independent orchestration paths (HTTP vm-agent and PowerShell Direct
with SHA-256 integrity checks). Validation relies on 194 automated tests, proxy detection
metrics on labeled synthetic profiles (precision/recall/F1), public MalwareBazaar IOC metadata,
a formal static benchmark (median 36.1~s, $n=5$), synthetic scoring profiles aligned with
\texttt{test\_risk\_scoring.py}, and benign execution via \texttt{benign-vm-test.exe} on
Path~B. The system emphasises explainability and local isolation over commercial cloud
sandboxes, targeting academic and laboratory use.

\vspace{0.8em}
\noindent\textbf{Keywords:} malware analysis; RAT; sandbox; Hyper-V; YARA; FastAPI;
software engineering; cybersecurity.

\chapter{Introduction}

\section{Context}

This report presents the final-year project in Computer Science Engineering at \ubi,
dedicated to the development of \rat: an integrated static and dynamic analysis platform
for detecting \emph{Remote Access Trojans} (RATs) in Windows executables (\texttt{.exe},
\texttt{.dll}) and, with reduced scope, C\# source files (\texttt{.cs}): on the web/API,
\texttt{.cs} files undergo string-based heuristics only (no PE imports or ILSpy); compilation
to \texttt{.exe} is available via the optional Tkinter GUI or manual build before upload.

RATs are among the most concerning classes of malware today: they allow an attacker to
remotely control a compromised system, harvest credentials, exfiltrate data, and execute
arbitrary commands. Their detection often requires combining \emph{offline} techniques
(static binary analysis) and \emph{online} techniques (behaviour observation in a controlled
environment), complemented by signature rules and scoring heuristics.

\rat\ was designed in an academic context as an \textbf{educational and triage} tool:
in addition to flagging risk indicators, it exposes decompiled code, structured reports, and
explanations of suspicious functions, enabling students and junior analysts to understand
\emph{why} a file is considered malicious. Complementarily, the web interface integrates a
\textbf{Google Gemini}-based assistant that allows users to ask, in natural language, about
the meaning of the pseudo-C excerpt visible in the results panel.

\section{Motivation}

The proliferation of malware with remote access capabilities demands accessible tools that
integrate multiple analysis layers into a single workflow. Commercial solutions such as
cloud sandboxes (VirusTotal, Any.Run, Hybrid Analysis) are powerful but often unsuitable for
teaching or local laboratory contexts, whether due to cost or sample confidentiality.

The motivation for this project rests on four pillars:

\begin{itemize}
    \item \textbf{Integration} - Unify static analysis, YARA rules, decompilation, and sandbox
          execution in a coherent ecosystem (API, web interface, desktop application).
    \item \textbf{Isolation} - Run potentially malicious samples in a Hyper-V VM without Internet
          connectivity, with automatic restore to a clean snapshot.
    \item \textbf{Transparency} - Produce detailed reports (imports, C2 strings, evasion,
          risk score, pseudo-C/IL) instead of a simple binary classification; optionally,
          support pseudo-C interpretation with an LLM assistant in the frontend.
    \item \textbf{Academic reproducibility} - Open source, extensive documentation, automated
          tests (pytest, Vitest, GitHub Actions CI), and security documentation
          (\texttt{docs/SEGURANCA.md}).
\end{itemize}

\section{Objectives}

The main objectives of the project are:

\begin{enumerate}
    \item Develop a Python \textbf{backend} (FastAPI) capable of receiving samples,
          running a complete static analysis pipeline, and orchestrating dynamic analysis jobs
          (\texttt{static}, \texttt{dynamic}, or \texttt{both}).
    \item Implement a \textbf{web interface} (React + Vite + TypeScript) with a
          \emph{drag-and-drop} zone, progress streaming, report visualisation, pseudo-C
          (Ghidra) and IL (.NET), a Gemini assistant to explain C code excerpts, and
          bilingual support (Portuguese/English).
    \item Provide a \textbf{WPF desktop application} (.NET~8) as an alternative entry point,
          including dependency bootstrap, persistent language selection, and integration with
          the Hyper-V sandbox.
    \item Build a \textbf{VM agent} (Minimal API .NET) and PowerShell scripts for isolated
          sample execution and behavioural telemetry collection.
    \item Define a \textbf{scoring model} (0--100) that aggregates multiple indicators
          (YARA, C2, evasion, packers, obfuscation, persistence).
    \item Validate the system with automated tests, benign samples (\texttt{benign-vm-test}),
          and operational documentation for local deployment.
\end{enumerate}

\chapter{State of the Art}
\label{ch:estado-arte}

\section{Background}

This chapter frames the application of malware analysis techniques in the cybersecurity domain,
with specific focus on RAT detection. It also examines the most widely used existing solutions
in this context --- static, dynamic, and hybrid --- comparing them with the approach adopted
in \rat.

\section{Malware Analysis: Overview}

Malware analysis is traditionally divided into two complementary approaches
\cite{skoudis2004,cipriano2019,anderson2012,moser2007}:

\begin{itemize}
    \item \textbf{Static analysis} - Examines the file without executing it: PE structure, sections,
          imports/exports, strings, entropy, YARA signatures, decompilation, and detection of
          evasion techniques (anti-debug, anti-VM).
    \item \textbf{Dynamic analysis} - Runs the sample in an isolated sandbox and monitors
          behaviour: process creation, registry changes, files, network, and persistence.
\end{itemize}

In the context of RATs, combining both approaches is especially relevant: static analysis
allows identification of suspicious imports (webcam access, keylogging, exfiltration via
\texttt{ws2\_32.dll}) and C2 strings without execution risk, while dynamic analysis
reveals actual behaviour --- established network connections, files created, persistence
registry keys.

\section{Trends in RAT and Malware Detection}

This section explores the most widely used and successful approaches for malware detection
and analysis, with particular attention to those closest to the RAT domain.

\subsection{Commercial and cloud sandboxes}

Platforms such as \emph{Any.Run} \cite{anyrun2024}, \emph{Hybrid Analysis} \cite{hybrid2019}, and
\emph{Joe Sandbox} \cite{joe2020} offer complete dynamic analysis with interactive reports,
building on earlier automated sandbox research \cite{bayer2006,willems2007}.
These platforms are powerful and rich in telemetry but present relevant limitations for
academic and laboratory contexts: high cost on professional plans, the need to submit samples
to external servers (compromising the confidentiality of sensitive samples), and inability to
customise the execution environment. \rat\ was designed precisely to address these gaps: local
execution, complete isolation, and zero cost.

\subsection{VirusTotal}

\emph{VirusTotal} \cite{virustotal2023} aggregates more than 70 antivirus engines and provides
static metadata and behavioural heuristics. It is the most widely used triage tool worldwide.
However, sample submission shares them with the platform's partners, which is unacceptable in
forensic investigation or proprietary sample analysis contexts. Furthermore, it does not expose
decompiled code or allow customisation of detection rules.

\subsection{Open-source frameworks}

\begin{itemize}
    \item \textbf{Cuckoo Sandbox} \cite{cuckoo2012} --- Self-hostable, extensible Python sandbox
          with support for behavioural analysis on Windows and Linux. It is the open-source
          reference closest to \rat, but requires complex configuration and does not integrate
          decompilation or explainable scoring.
    \item \textbf{CAPE Sandbox} \cite{cape2021} --- Cuckoo fork focused on extracting configurations
          from malware families and C2 servers. Highly specialised; not suitable as a generalist
          educational tool.
    \item \textbf{YARA} \cite{yara2023} --- Rule language for pattern-based detection, used by
          virtually all analysis platforms. \rat\ integrates YARA as one phase of the static
          pipeline, combining it with scoring and decompilation.
    \item \textbf{Ghidra / ILSpy} \cite{ghidra2019,ilspy2024} --- Decompilers for native binaries
          and .NET, respectively. Essential tools in manual analysis, but typically used in
          isolation on the command line. \rat\ orchestrates both and exposes the results
          directly in the web interface.
\end{itemize}

\subsection{Machine learning-based detection}

Recent work applies \emph{deep learning} to static PE file features for automatic malware
classification \cite{raff2018,ucar2020,ucci2019,apruzzese2018}. These approaches achieve high classification metrics
but produce opaque decisions --- the analyst knows the file was classified as malicious, but
not why. \rat\ prioritises \textbf{explainability} through concrete indicators (suspicious
imports, C2 strings, YARA results, pseudo-C) and an optional LLM assistant that helps interpret
decompiled code. Public threat-intelligence repositories such as MalwareBazaar \cite{abusech2021}
complement local analysis by providing family labels and SHA-256 hashes without requiring sample
execution in the academic repository. Large-scale malware labeling tools such as AVclass
\cite{mohaisen2016} illustrate how family attribution at scale complements local triage, while
ransomware and trojan surveys \cite{vinod2019} contextualise the broader remote-access threat
landscape that RAT families inhabit.

\section{Advantages of the Proposed Solution}

For this project, a deliberately distinct approach was chosen from commercial solutions and
existing generic frameworks. Instead of replicating a conventional sandbox, \rat\ combines
multi-phase static analysis with native Hyper-V sandbox and integrated decompilation, all
exposed in an accessible web interface and a WPF desktop application.

\begin{table}[H]
    \centering
    \caption{Comparison of the \rat\ solution with existing alternatives}
    \label{tab:comparacao}
    \small
    \begin{tabular}{@{}p{2.2cm}p{4.5cm}p{5.5cm}@{}}
        \toprule
        \textbf{Reference} & \textbf{Technology} & \textbf{\rat\ solution} \\
        \midrule
        VirusTotal & Cloud multi-AV & Local; YARA + heuristics + Hyper-V sandbox \\
        Cuckoo/CAPE & Self-hostable sandbox & Native Windows sandbox (Hyper-V) \\
        Any.Run / Hybrid & Commercial sandbox & Free; educational focus; pseudo-C/IL \\
        YARA standalone & Signature rules & YARA + scoring + decompilation \\
        Ghidra/ILSpy CLI & Offline decompilation & Orchestrated decompilation + web UI \\

        \bottomrule
    \end{tabular}
\end{table}

In summary, adopting Hyper-V as the sandbox hypervisor eliminates the need for external
infrastructure; integrating Ghidra and ILSpy directly into the pipeline makes decompilation
accessible without manual tool installation; and the Gemini assistant transforms pseudo-C into
an interactive educational resource, differentiating \rat\ from any existing solution.

\section{Conclusions}

The state of the art confirms that effective RAT detection benefits from multi-layer analysis.
Commercial solutions are powerful but inaccessible in academic contexts; open-source frameworks
are flexible but require significant manual integration. \rat\ positions itself as a local,
integrated, and explainable platform, suitable for university laboratories, cybersecurity
training, and initial triage of suspicious executables.

\chapter{Technologies and Tools Used}
\label{ch:tecnologias}

\section{Introduction}

This chapter summarises the main technologies and tools used in the development of
\rat, namely in building the backend, user interfaces, dynamic analysis sandbox, and
project report.

\section{Python and FastAPI}

\textbf{Python~3.10+} was adopted as the main backend language, due to its maturity in the
information security ecosystem and the wide availability of libraries for PE file analysis,
binary format parsing, and integration with decompilation tools.
\textbf{FastAPI} \cite{fastapi2024} was chosen as the web framework for providing automatic
data validation with Pydantic, interactive OpenAPI documentation (\texttt{/docs}), and native
support for asynchronous NDJSON streaming (\texttt{/api/analyze\_stream}), essential for
real-time feedback during analysis. There is also an optional graphical interface in
\textbf{Tkinter} (\texttt{backend/gui/rat\_analyzer\_gui.py}) for local static analysis without
a browser, useful for quick demonstrations.

\section{React, Vite and TypeScript}

The web interface was built with \textbf{React~18} and \textbf{TypeScript}, ensuring static
typing that reduces errors during development. The \textbf{Vite} bundler enables instant hot-reload
during development and optimised production builds. For visual styling,
\textbf{Tailwind CSS} and \textbf{shadcn/ui} were adopted; transition animations are handled
with \textbf{Framer Motion}. The unit test suite uses \textbf{Vitest} with more than 56 tests.
Integration with \textbf{Google Gemini} (\texttt{gemini-2.0-flash}) is done directly in the
browser: the user's API key is stored in \texttt{localStorage} and never passes through the
FastAPI backend, ensuring the server has no access to third-party credentials.

\section{.NET~8, WPF and Minimal API}

Three .NET~8 projects share the \texttt{RatAnalyzer.sln} solution: \textbf{Rat Analyzer}
(WPF desktop, compiles to \texttt{Rat Analyzer.exe}), \textbf{VmAgent} (Minimal API running inside the sandbox
VM to receive and execute samples), and \textbf{BenignVmTest} (benign executable to validate
the dynamic pipeline without risk). WPF serves as an alternative entry point to the web
interface, with automatic dependency bootstrap, persistent language selection, and direct
integration with the Hyper-V sandbox.

\section{YARA, Ghidra and ILSpy}

\textbf{YARA} \cite{yara2023} is the pattern-matching rule language used for signature-based
detection. Rules reside in \texttt{yara\_rules/} and are compiled and applied to the binary under
analysis. \textbf{ILSpy CLI} \cite{ilspy2024} decompiles .NET assemblies into readable C\#
code, enabling inspection of executables written with the managed runtime.
\textbf{Ghidra~12+} \cite{ghidra2019}, developed by the NSA, is used for decompilation of
native PE binaries, producing pseudo-C that is exposed in the web interface code panel.

\section{Hyper-V, PowerShell and SQLite}

The dynamic sandbox relies on \textbf{Hyper-V}, the native Windows hypervisor, with a VM named
\texttt{MalwareSandbox}, connected to an \textbf{Internal} switch with no Internet connectivity
on the guest and a \texttt{CleanState} snapshot that is restored before each analysis.
\textbf{PowerShell} automates one-time VM setup (\texttt{01-Setup-MalwareSandbox.ps1}) and,
on \textbf{Path~B}, sample copy, guest execution, and report transfer
(\texttt{04-Run-Sample.ps1}). On \textbf{Path~A}, the Python backend
(\texttt{vm\_drivers/hyperv.py}) uses PowerShell only for snapshot restore and VM start;
sample upload, execution, and report retrieval go through the HTTP vm-agent.
\textbf{SQLite} persists analysis jobs in \texttt{analysis.db}; \textbf{Redis}
with \textbf{RQ} is a configurable option for distributed queuing in environments with multiple workers.

The backend selects the sandbox driver at runtime via \texttt{SANDBOX\_VM\_DRIVER}; the orchestrator
delegates to \texttt{HyperVVMDriver} without changing the rest of the job pipeline:

\begin{lstlisting}[style=python,caption={VM driver selection - \texttt{vm\_orchestrator.py}},label={lst:vm-orchestrator}]
def run_dynamic_analysis(job: AnalysisJob) -> Dict[str, Any]:
    driver = _build_driver()  # stub | hyperv | proxmox (experimental)
    out: DynamicAnalysisOutput = driver.run(job)
    return {"summary": out.summary, "behavior": out.behavior, "driver": driver.name}
\end{lstlisting}

\section{GitHub and LaTeX}

\textbf{GitHub} hosts the project repository, with Git version control and continuous integration
via \textbf{GitHub Actions} (CI with pytest, Vitest, and dotnet build). Changes are recorded in
\texttt{CHANGELOG.md} and contribution conventions in \texttt{CONTRIBUTING.md}. This report was
written in \textbf{\LaTeX}, a typesetting system widely used in academic and scientific contexts,
which automatically manages section numbering, figures, tables, and bibliographic references
with rigour and consistency.

\section{Security and Isolation}

The design adopts \emph{fail-closed} in production: the backend refuses to start without
\texttt{RATANALYZER\_API\_TOKEN} when \texttt{RATANALYZER\_ENV=production}; the vm-agent
refuses to start without \texttt{VM\_AGENT\_TOKEN}, except when
\texttt{VM\_AGENT\_ALLOW\_INSECURE=1} in local development.

Secrets reside in \texttt{secrets/} (gitignored) and are produced by
\texttt{generate-production-secrets.ps1} under \texttt{scripts/}. HTTP uploads require
authentication, with name sanitisation, size limits, and storage in \texttt{DATA\_DIR}
outside the repository. The canonical security documentation is in \texttt{docs/SEGURANCA.md}.

\section{Technology choices and rejected alternatives}

Table~\ref{tab:tech-choices} summarises major stack decisions and why simpler or more common
alternatives were not adopted. The goal was a \textbf{local}, \textbf{Windows-native} platform
for academic laboratories rather than a cloud-first or containerised product.

\begin{table}[H]
    \centering
    \caption{Technology choices and rejected alternatives}
    \label{tab:tech-choices}
    \small
    \begin{tabular}{@{}p{2.4cm}p{3.6cm}p{3.8cm}p{3.6cm}@{}}
        \toprule
        \textbf{Area} & \textbf{Chosen} & \textbf{Rejected} & \textbf{Rationale} \\
        \midrule
        Sandbox & Hyper-V + snapshot & Docker, Cuckoo VM & Native Windows telemetry; no Linux guest for PE/RAT behaviour \\
        API & FastAPI + Pydantic & Flask, Django & Async NDJSON streaming; automatic OpenAPI \\
        Frontend & React + Vite + TS & Vue, Angular & Team familiarity; Vitest/Playwright ecosystem \\

        Queue & Optional Redis/RQ & Mandatory Celery & Works offline with local threads (NFR~06) \\
        Decompiler & ILSpy + Ghidra & IDA Pro only & Open source; IDA deferred to future work \\

        \bottomrule
    \end{tabular}
\end{table}

Docker was explicitly excluded: malware sandboxes require GUI/process behaviour on Windows,
and Hyper-V isolation is already available on laboratory hosts. A backend LLM proxy would
centralise API keys but would route pseudo-C excerpts through the server; the client-side
design keeps decompiled code local except for the excerpt the user chooses to send.

\section{Conclusion}

The multi-language stack reflects the heterogeneous nature of malware analysis: Python for
pipeline and API, TypeScript for user experience, C\# for integration with the Windows and
Hyper-V ecosystem, and PowerShell for infrastructure automation. The combination of these
technologies enabled building a coherent platform with clear separation of responsibilities
and extensive documentation.

This chapter aims to detail the decisions taken regarding system architecture and design during

\subsection{Non-Functional Requirements}

The Non-Functional Requirements (NFR) were organised into the following categories, taking into
account the quality attributes most relevant to the malware analysis context:

\begin{description}[style=nextline, leftmargin=0cm]
    \item[\nfr{01} - Security] The API must bind only to the local address
          (\texttt{127.0.0.1}); authentication tokens mandatory in production
          (\texttt{RATANALYZER\_API\_TOKEN}, \texttt{VM\_AGENT\_TOKEN}); secrets
          never versioned in the Git repository.
    \item[\nfr{02} - Isolation] The sandbox VM must be connected to an \textbf{Internal} switch
          with no Internet routing to the guest; on \textbf{Path~B}, a network \emph{preflight}
          runs before each sample (\texttt{RunSample/PhaseA-Setup.ps1}); Path~A relies on
          correct manual VM configuration; automatic restore to \texttt{CleanState} snapshot
          after each dynamic analysis.
    \item[\nfr{03} - Usability] The web interface must support \emph{drag-and-drop};
          must provide real-time feedback during analysis; must be responsive and
          accessible in modern browsers. A user with basic information security knowledge
          should be able to submit and interpret an analysis without additional training.
    \item[\nfr{04} - Performance] The system must support at least 2 concurrent workers
          in default mode (configurable); execution timeouts must be configurable per path:
          Path~A defaults to 300~s (\texttt{SANDBOX\_DYNAMIC\_TIMEOUT\_SECONDS});
          Path~B defaults to 120~s per sample (\texttt{TimeoutSeconds} in
          \texttt{04-Run-Sample.ps1}) with a 900~s global cap; VM restore/start operations
          use a separate 120~s timeout (\texttt{SANDBOX\_VM\_OP\_TIMEOUT\_SECONDS}).
    \item[\nfr{05} - Maintainability] The project must include automated CI tests
          (pytest, Vitest, dotnet build); dependency locks with hashes for reproducible
          integrity; and extensive technical documentation versioned in the repository.
    \item[\nfr{06} - Availability] Redis queue mode must be optional and the
          system must work without it, falling back to local threads.
\end{description}

\section{Security Architecture}
\label{sec:seguranca}

Figure~\ref{fig:trust-zones} models three zones: \textbf{host} (components under operator control),
\textbf{sandbox network} (Hyper-V Internal switch, API$\leftrightarrow$vm-agent traffic), and
\textbf{guest} (untrusted environment where the sample executes). Internet is not routed to the
guest; each run begins with \emph{restore} to the \texttt{CleanState} snapshot.

Figure~\ref{fig:auth} summarises authentication mechanisms. The backend validates
\texttt{X-API-Token}; the vm-agent validates \texttt{X-Agent-Token} with constant-time comparison
(\texttt{TokenComparer.cs}); Hyper-V scripts use guest credentials via PowerShell Direct. The
\texttt{stub} driver does not execute samples and does not require sandbox authentication.

Before invoking \texttt{Restore-VMSnapshot} or \texttt{Start-VM}, the Hyper-V driver validates
VM and snapshot names against a strict allowlist to block PowerShell injection
(Listing~\ref{lst:hyperv-validate}):

\begin{lstlisting}[style=python,caption={Hyper-V name allowlist - \texttt{vm\_drivers/hyperv.py}},label={lst:hyperv-validate}]
_SAFE_PS_NAME_RE = re.compile(r"^[A-Za-z0-9 ._\-]+$")

def _validate_cfg(self) -> None:
    if not sys.platform.startswith("win"):
        raise RuntimeError("Driver Hyper-V só é suportado em Windows.")
    for label, value in (
        ("HYPERV_VM_NAME", self.cfg.vm_name),
        ("HYPERV_SNAPSHOT_NAME", self.cfg.snapshot_name),
    ):
        if not _SAFE_PS_NAME_RE.match(value):
            raise ValueError(f"{label} contém caracteres inválidos.")
\end{lstlisting}

On the guest, uploads are confined to \texttt{samples/} through canonical path resolution in
\texttt{SampleStorage.cs}, preventing \emph{path traversal} even if the filename contains
\texttt{..} or absolute segments:

\begin{lstlisting}[style=csharp,caption={Safe sample path resolution - \texttt{vm-agent/Services/SampleStorage.cs}},label={lst:sample-storage}]
public static bool TryResolveTargetPath(string safeName, out string targetPath, out string? error)
{
    if (string.IsNullOrWhiteSpace(safeName) || safeName.Contains(".."))
    {
        error = "Nome de ficheiro inválido.";
        return false;
    }
    var baseDir = SamplesDirectory;
    targetPath = Path.GetFullPath(Path.Combine(baseDir, safeName));
    if (!targetPath.StartsWith(baseDir + Path.DirectorySeparatorChar, ...))
    {
        error = "Caminho de destino inválido.";
        return false;
    }
    return true;
}
\end{lstlisting}

\section{Backend - Static Analysis Pipeline}

The \texttt{RATAnalyzer} class (\texttt{backend/rat\_analyzer.py}) orchestrates the 7-phase pipeline:

\begin{enumerate}
    \item PE metadata extraction (\texttt{file\_info}).
    \item .NET decompilation via ILSpy (for \texttt{.exe}/\texttt{.dll} only).
    \item Static analysis - suspicious imports, C2 strings, anti-debug/anti-VM, entropy.
    \item Deobfuscation - Base64, XOR, obfuscation indicators.
    \item YARA scan over \texttt{yara\_rules/}.
    \item Score calculation via \texttt{risk\_scorer.py}.
    \item Report generation (\texttt{report\_generator.py}), preceded when needed by native
          disassembly and Ghidra pseudo-C (sub-steps \texttt{[7a]/[7b]} in
          \texttt{rat\_analyzer.py}, after scoring, if ILSpy did not produce managed code).
\end{enumerate}

For \texttt{.cs} uploads via the web/API, phase~2 is skipped and Ghidra is not applied;
only string-based heuristics from phase~3 contribute to the report.

The FastAPI API (\texttt{backend/api.py} via \texttt{app\_factory.py}) exposes REST endpoints
documented in OpenAPI (\texttt{/docs}), organised in \texttt{routers/} (\texttt{analyze},
\texttt{jobs}, \texttt{health}, \texttt{storage}). Fallback messages and user-readable errors are
localised (PT/EN) via \texttt{i18n.py} and \texttt{RATANALYZER\_LANG}. Table~\ref{tab:api-endpoints}

\subsection{Path A - Backend + HTTP vm-agent}

\texttt{vm\_orchestrator.py} selects the driver via \texttt{SANDBOX\_VM\_DRIVER}
(\texttt{stub} by default, \texttt{hyperv}, or experimental \texttt{proxmox}). With
\texttt{hyperv}, the host restores the snapshot, starts the VM, and communicates with the vm-agent on
endpoints \texttt{/api/health}, \texttt{/api/upload}, \texttt{/api/run}, and
\texttt{/api/report}, always with \texttt{X-Agent-Token} header. The agent limits uploads to
200~MB, prevents \emph{path traversal} in \texttt{samples/}, and serialises executions via
\texttt{RunGate} (one run at a time).

Listing~\ref{lst:hyperv-run} shows the five-step sequence in \texttt{HyperVVMDriver.run}: restore
snapshot, start VM, wait for agent health, upload sample, execute, and fetch report.

\begin{lstlisting}[style=python,caption={Hyper-V driver orchestration - \texttt{vm\_drivers/hyperv.py}},label={lst:hyperv-run}]
def run(self, job: "AnalysisJob") -> DynamicAnalysisOutput:
    self._validate_cfg()
    self._ps(
        f'Restore-VMSnapshot -VMName "{self.cfg.vm_name}" '
        f'-Name "{self.cfg.snapshot_name}" -Confirm:$false',
        timeout=self.cfg.vm_op_timeout_seconds,
    )
    self._ps(f'Start-VM -Name "{self.cfg.vm_name}" | Out-Null', ...)
    self._wait_for_agent_ready(...)
    self._agent_upload(job)
    self._agent_run(timeout_seconds=self.cfg.dynamic_timeout_seconds)
    behavior = self._agent_get_report()
    return DynamicAnalysisOutput(summary=..., behavior=behavior)
\end{lstlisting}

Inside the guest, \texttt{/api/run} acquires \texttt{RunGate} before launching the sample process;
concurrent runs receive HTTP~409. Listing~\ref{lst:vm-agent-run} summarises the endpoint and
Listing~\ref{lst:sample-runner} the execution with configurable timeout.

\begin{lstlisting}[style=csharp,caption={Serialised execution endpoint - \texttt{AgentEndpoints.cs}},label={lst:vm-agent-run}]
app.MapPost("/api/run", async (RunRequest req, AnalysisState state, RunGate gate) =>

var timeoutSeconds = Math.Min(req.TimeoutSeconds, AgentLimits.MaxRunTimeoutSeconds);

\subsection{Path B - PowerShell Scripts}

\texttt{04-Run-Sample.ps1} executes phases A--G: setup, VM boot, sample and script copy,
detached execution on guest, wait for \texttt{guest\_analysis\_done.txt}, report copy
guest$\rightarrow$host via \textbf{PowerShell Direct} or \texttt{Copy-VMFile}, \textbf{SHA256}
verification after copy, and \texttt{try/finally} cleanup.

Flow inside the VM (\texttt{vm/Run-MalwareAnalysis.ps1}):
\begin{itemize}
    \item Baseline of processes, files, registry, and network (with \textbf{Sysmon}
          \cite{sysmon2022} when installed on guest).
    \item Sample execution with configurable timeout.
    \item Post-execution diff; \texttt{REPORT\_END;} marker and
          \texttt{guest\_analysis\_done.txt} file with \texttt{reportSha256} and \texttt{reportBytes}.
\end{itemize}

The host validates integrity by comparing the hash and size of the copied file with the digest
recorded on the guest; on discrepancy, the report on the host is discarded. The typical destination
is \texttt{D:\textbackslash PROJETOVM\textbackslash Reports\textbackslash analysis\_<RunId>.txt};
the run JSON records \texttt{report\_sha256} and \texttt{report\_hash\_verified}.

When analysis finishes inside the guest, \texttt{Run-MalwareAnalysis.ps1} writes
\texttt{guest\_analysis\_done.txt} with the report digest computed \textbf{before} host-side copy
(Listing~\ref{lst:guest-done-write}). The host then validates the transferred file against that
digest (Listing~\ref{lst:sha256-verify}); on mismatch the report is discarded.

\begin{lstlisting}[style=powershell,caption={Guest completion marker - \texttt{vm/Run-MalwareAnalysis.ps1}},label={lst:guest-done-write}]
$reportSha256 = (Get-FileHash -LiteralPath $ReportPath -Algorithm SHA256).Hash
$reportBytes = [long](Get-Item -LiteralPath $ReportPath).Length
@{
    finishedUtc  = (Get-Date).ToUniversalTime().ToString('o')
    reportPath   = $ReportPath
    reportSha256 = $reportSha256
    reportBytes  = $reportBytes
    transport    = "psdirect"
} | ConvertTo-Json -Compress | Set-Content -LiteralPath $guestDonePath -Encoding UTF8
\end{lstlisting}

\begin{lstlisting}[style=powershell,caption={Post-transfer SHA-256 verification - \texttt{SandboxCommon/VmFileTransfer.ps1}},label={lst:sha256-verify}]
function Assert-SandboxCopiedReportHash {
    param([string] $HostReportPath, [string] $ExpectedSha256, [long] $ExpectedBytes = 0)
    if ([string]::IsNullOrWhiteSpace($ExpectedSha256)) {
        throw "Digest SHA256 do guest ausente; não é possível validar a cópia do relatório."
    }
    if ($ExpectedBytes -gt 0) {
        $hostBytes = [long](Get-Item -LiteralPath $HostReportPath).Length
        if ($hostBytes -ne $ExpectedBytes) { throw "Tamanho do relatório copiado não coincide." }
    }
    return (Assert-FileSha256 -Path $HostReportPath -ExpectedSha256 $ExpectedSha256 ...)
}
\end{lstlisting}

\subsubsection{Previous transport approaches}
\label{sec:caminho-b-historico}

Previous iterations of Path B explored sending the text report via \textbf{COM1} port mapped to a
\textbf{Named Pipe} on the host (\texttt{Send-ReportViaCom.ps1}, protocol \texttt{START\_OF\_REPORT}
\ldots{} \texttt{END\_OF\_REPORT}), with \texttt{Copy-VMFile} as fallback when the pipe expired.
In practice, direct copy via PsDirect proved more reliable (including on VMs where the COM1/pipe
pair failed); serial transport was \textbf{discontinued} in favour of copy with post-transfer
cryptographic verification. Legacy code (\texttt{SandboxCommon/SerialPipe.ps1},
\texttt{02-Host-ReceiveReport.ps1}) remains in the repository for reference only. Technical
detail: \texttt{SERIAL\_REPORT\_PROTOCOL.md}.

\section{Main Conclusions}

Upon completing this project, I can affirm that it was an extraordinarily enriching learning
experience, which allowed me to consolidate and expand knowledge in domains that, at the start of
development, I only partially mastered --- from malware engineering and PE file analysis, to
virtual machine orchestration with Hyper-V, to designing asynchronous APIs with streaming, and
building modern web interfaces in TypeScript/React. The project required me to grow both as a
Computer Science Engineering student and, certainly, as a future professional in the field.

\rat\ achieved the \textbf{implementation} objectives defined initially: it is an integrated
static and dynamic analysis platform for RAT detection, with the following concrete results:

\begin{itemize}
    \item \textbf{Complete static pipeline} - 7 implemented phases (PE metadata, ILSpy,
          import and C2 string analysis, deobfuscation, YARA scan, scoring, native/Ghidra when
          needed, and report),
          with 90 automated backend tests.
    \item \textbf{Isolated Hyper-V sandbox} - Two independent and complementary orchestration paths
          (HTTP via vm-agent and PowerShell Direct), with automatic restore to clean snapshot
          and SHA-256 cryptographic verification of transferred report integrity.
    \item \textbf{Functional web and desktop interfaces} - React interface with progress streaming,
          three results panels, and Gemini assistant; WPF application as alternative entry point
          with automatic dependency bootstrap.
    \item \textbf{Comprehensive test coverage} - 90 pytest tests in backend, 56 Vitest tests in
          frontend, E2E tests with Playwright, and 48 xUnit tests in .NET components
          (30 vm-agent, 12 WPF, 6 benign-vm-test).
    \item \textbf{Extensive technical documentation} - PlantUML diagrams synchronised with the report
          (10 figures in chapter~4), security architecture documented in
          \texttt{docs/SEGURANCA.md}, and operational guides for local deployment.
    \item \textbf{Explainable indicators} - Risk score 0--100 with breakdown by factor,
          pseudo-C/IL accessible in browser, and optional LLM assistant for interpretation of
          suspicious code; the user understands \emph{why} a file is considered dangerous.
\end{itemize}

\section{Limitations}

Despite the results obtained, relevant limitations are acknowledged:

\begin{itemize}
    \item Empirical validation relies on benign samples, synthetic profiles, and public IOC
          metadata (MalwareBazaar hashes without sample execution); detection rates against
          real malware binaries were not measured for legal and isolation reasons.
    \item Path A (vm-agent) records more limited behavioural telemetry than Path B and does not
          run the network-isolation preflight implemented on Path~B.
    \item \texttt{.cs} uploads via the web/API receive string heuristics only; full ILSpy/Ghidra
          analysis requires a compiled \texttt{.exe}/\texttt{.dll}.
    \item Heuristic scoring may produce false positives on legitimate binaries with network
          imports; filters were implemented (e.g.\ exclusion of Microsoft URLs in C2).
    \item Dynamic analysis requires Hyper-V and manual VM configuration, which limits portability.
\end{itemize}

\section{Future Work}

This project will be refined and potentially used in an academic context at \ubi,
serving as a support tool for information security curriculum units.

Regarding future work, several improvements could be implemented to make the platform even more
robust and complete:

\begin{enumerate}
    \item \textbf{IDA Pro integration} - Ghidra is already integrated, but IDA Pro offers deeper
          analysis for complex malware families; integration via plugin or REST API would be a
          natural next step.
    \item \textbf{Advanced deobfuscation and automatic C2 config extraction} - Automatically identify
          command-and-control domains, IPs, and ports from encrypted configurations embedded in
          samples.
    \item \textbf{Enriched dynamic telemetry} - Integrate Sysmon, ETW, and system call hooking in
          the vm-agent for more granular behavioural telemetry capture (currently Path A records
          only process and stdout/stderr).
    \item \textbf{Support for more formats} - Expand the pipeline to PDF documents, Office macros,
          PowerShell/VBScript scripts, and Android APKs.
    \item \textbf{Known signature database} - Integrate a database of SHA-256 hashes of known malware
          (MALPEDIA, MalwareBazaar) for direct matching in the metadata phase.
    \item \textbf{C2 network traffic analysis} - Capture and analyse traffic generated by the sample
          during dynamic execution, identifying C2 protocols and communication patterns.
    \item \textbf{Gemini assistant evolution} - Migrate the proxy to the backend for environments
          without API key exposure in the browser; support other LLM models (Llama, Mistral);
          add automatic explanations of suspicious functions without user input.
    \item \textbf{YARA rule management interface} - Allow users to create, edit, and test YARA rules
          directly in the web interface, without manually editing files in the filesystem.
\end{enumerate}

In conclusion, the extension potential of this platform is vast: from integration with incident
response pipelines (SOAR), to use as a CTF tool in cybersecurity competitions, or even adaptation
for analysis of other types of malicious files. \rat\ constitutes a solid and extensible foundation
for future exploration.

\section{Token verification in vm-agent}

\begin{lstlisting}[caption={Authentication middleware - \texttt{vm-agent/Security/AgentTokenMiddleware.cs}},label={lst:vm-agent-token}]
public static void UseAgentTokenAuth(this WebApplication app, string? agentToken)
{
    app.Use(async (context, next) =>
    {
        if (!string.IsNullOrWhiteSpace(agentToken))
        {
            if (!context.Request.Headers.TryGetValue("X-Agent-Token", out var provided) ||
                !TokenComparer.FixedTimeEquals(provided.ToString(), agentToken))
            {
                context.Response.StatusCode = StatusCodes.Status401Unauthorized;
                await context.Response.WriteAsJsonAsync(new
                    { detail = "Invalid or missing token (header X-Agent-Token)." });
                return;
            }
        }
        await next();
    });
}
\end{lstlisting}

\section{RunGate - serialised execution}

The \texttt{RunGate} uses a \texttt{SemaphoreSlim(1,1)} with non-blocking acquisition
(\texttt{WaitAsync(0)}): if a run is already in progress, \texttt{/api/run} returns HTTP~409
without queueing a second sample.

\begin{lstlisting}[style=csharp,caption={Single-run gate - \texttt{vm-agent/State/RunGate.cs}},label={lst:run-gate}]
public sealed class RunGate
{
    private readonly SemaphoreSlim _gate = new(1, 1);

    public async Task<bool> TryEnterAsync() => await _gate.WaitAsync(0);

    public void Release() => _gate.Release();
}
\end{lstlisting}

\section{Hyper-V driver - agent HTTP client}

Listing~\ref{lst:hyperv-agent} shows how the host uploads the sample and polls the behavioural
report after the VM is ready. Every request includes \texttt{X-Agent-Token} when configured.

\begin{lstlisting}[style=python,caption={VM agent HTTP calls - \texttt{vm\_drivers/hyperv.py}},label={lst:hyperv-agent}]
def _agent_upload(self, job: "AnalysisJob") -> None:
    with open(job.sample_path, "rb") as f:
        files = {"file": (job.sample_path.name, f, "application/octet-stream")}
        r = requests.post(self._agent_url("/api/upload"), files=files,
                          headers=_agent_headers(), timeout=...)
    if not r.ok:
        raise RuntimeError(f"Upload para VM agent falhou ({r.status_code})")

def _agent_get_report(self) -> Any:
    r = requests.get(self._agent_url("/api/report"), headers=_agent_headers(), ...)
    return r.json()

\section{Report transfer protocol (Path B)}

\subsection{Current implementation}

After analysis, the guest writes \texttt{C:\textbackslash analysis.txt} and
\texttt{C:\textbackslash analysis\_work\textbackslash guest\_analysis\_done.txt} (JSON with
\texttt{reportSha256}, \texttt{reportBytes}, \texttt{transport=psdirect}). The host copies the
report with PsDirect or \texttt{Copy-VMFile} and accepts the file only if SHA256 and size match
the guest digest.

\subsection{Previous approaches (archive)}

Earlier versions sent the report \textbf{line-by-line} via COM1:
\texttt{START\_OF\_REPORT} \textrightarrow{} content lines \textrightarrow{}
\texttt{END\_OF\_REPORT}, with \texttt{Copy-VMFile} as fallback. This design required a
Generation~1 VM for the COM1/pipe pair and proved less robust than direct copy with hash
(see subsection~\ref{sec:caminho-b-historico} in the implementation chapter).
